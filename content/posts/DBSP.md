## 第一章 绪论

### 1.1 数据库系统的基本概念

#### 数据（Data）

- 描述事物的符号记录，是数据库中存储、用户操纵的基本单位
- 数据的含义称为数据的**语义**，数据与其语义不可分

#### 数据库（DB - Data Base）

- 按一定结构组织存储的、**集成的、可共享**的数据集合
- 基本特征：
  - 数据按一定的数据模型组织、描述和储存
  - 可为各种用户共享
  - 冗余度较小
  - 数据独立性较高
  - 易扩展

#### 数据库管理系统（DBMS - Data Base Management System）

- 管理和维护数据库的**系统软件**
- 位于用户与操作系统之间的一层数据管理软件
- 用途：科学地组织和存储数据、高效地获取和维护数据
- 常见产品：Oracle、SQL Server、MySQL、DB2等

#### 数据库系统（DBS - Data Base System）

- 在计算机系统中引入数据库后的系统构成
- 组成：数据库 + DBMS（及其开发工具）+ 应用系统 + 数据库管理员（DBA）+ 用户

**三者关系：** DB ⊂ DBMS ⊂ DBS（DBS包含DBMS，DBMS管理和维护DB）

---

### 1.2 数据管理技术的发展阶段

| 阶段    | 时间           | 硬件        | 软件   | 特点                   |
| ----- | ------------ | --------- | ---- | -------------------- |
| 人工管理  | 50年代中期以前     | 无直接存取存储设备 | 无OS  | 数据不保存、程序管理数据、无独立性    |
| 文件系统  | 50年代中至60年代后期 | 磁盘、磁鼓     | 文件系统 | 数据冗余度大、共享困难、独立性差     |
| 数据库系统 | 60年代后期至今     | 大容量磁盘     | DBMS | 数据结构化、共享性高、独立性强、统一管理 |

#### 数据库系统的四大特点

1. **数据结构化、集成化**：数据按数据模型组织，面向整个应用系统
2. **数据共享性高、冗余度低、易扩充**：并发共享
3. **数据独立性高**：由三级模式两级映像保证
4. **数据由DBMS统一管理和控制**：安全性、完整性、并发控制、数据库恢复

#### 文件系统 vs 数据库系统

- **相同点**：都以文件为基本单位存储；都有逻辑/物理结构之分；都有专门软件管理
- **不同点**：数据库面向整个应用系统组织，减少冗余实现共享；逻辑结构分局部和全局两级；DBMS管理功能远比文件系统强大

### 1.3 数据模型

#### 两类模型（按应用目的）

- **概念模型（信息模型）**：如E-R模型，从用户角度对数据建模，用于数据库设计
- **逻辑模型（数据模型）**：如层次、网状、关系模型，从计算机角度建模，用于DBMS实现

#### 信息的三个世界

```
现实世界 →（认识、分析、抽象）→ 信息世界（概念模型）→（描述、规范、转换）→ 机器世界（数据模型）
```

#### 信息世界基本概念

- **实体**：客观存在并能相互区别的事物
- **属性**：实体所具有的某一特征（简单/复合、单值/多值、存储/派生）
- **码（键/Key）**：能唯一标识实体的最小属性集
- **实体型**：由实体名及其属性名集表示
- **实体集**：同类型实体的集合

#### 实体型间的联系

- **1:1**：如 系 — 系主任
- **1:n**：如 班级 — 学生
- **m:n**：如 学生 — 课程

#### E-R图的四个基本成分

- **矩形框**：表示实体型
- **椭圆形**：表示属性
- **菱形**：表示联系
- **连线**：连接实体与联系，或实体与属性

---

### 1.4 数据模型的三要素

1. **数据结构**（描述数据库的**静态特性**）：描述数据库的组成对象及对象之间的联系
2. **数据操作**（描述数据库的**动态特性**）：对数据库对象允许执行的操作集合（查询、插入、删除、修改）
3. **数据的完整性约束**：一组完整性规则的集合，保证数据的正确、有效、相容

---

### 1.5 三种基本数据模型

| 特征      | 层次模型 | 网状模型  | 关系模型    |
| ------- | ---- | ----- | ------- |
| 数据结构    | 树形结构 | 图/系结构 | 二维表     |
| 联系表示    | 指针链接 | 指针链接  | 二维表     |
| 出现年代    | 1968 | 1969  | 1970    |
| 理论基础    | 无    | 无     | 关系规范化理论 |
| 查询效率    | 较高   | 较高    | 较低（需优化） |
| 数据独立性   | 较差   | 较差    | 较高      |
| DML操作方式 | 过程式  | 过程式   | 非过程式    |

#### 层次模型

- 最早出现的数据模型，树形结构
- **缺点**：多对多联系不自然、插入删除限制多、查询需经过双亲结点
- **操作规则**：无双亲不能插子女；删双亲则子女无

#### 网状模型

- 采用DBTG系结构，允许多双亲、多联系
- **优点**：更直接描述现实世界，存取效率高
- **缺点**：结构复杂，DDL/DML语言复杂

#### 关系模型

- 数据的逻辑结构是一张二维表，由行和列组成
- **基本术语**：关系(表)、元组(行)、属性(列)、分量(原子值)
- **优点**：严格的数学基础、概念单一、存取路径透明、数据独立性高
- **缺点**：查询效率需优化，开发DBMS难度大
- **最基本规范条件**：关系的每一个分量必须是不可分的数据项（不允许表中有表）

---

### 1.6 数据库系统的三级模式结构

#### 三级模式

1. **外模式（子模式/用户模式）**：对局部数据逻辑结构和特征的描述（**多个**）
2. **模式（逻辑模式）**：对全局数据逻辑结构和特征的描述（**一个**）
3. **内模式（存储模式/物理模式）**：对数据物理结构和存储方式的描述（**一个**）

#### 二级映像

1. **外模式/模式映像**：模式变 → 修改映像使外模式不变 → 保证**数据逻辑独立性**
2. **模式/内模式映像**：存储结构变 → 修改映像使模式不变 → 保证**数据物理独立性**

> **数据独立性**：数据结构与应用程序之间相互独立的特性，即数据结构的修改不引起应用程序的修改。

#### 三级模式间的联系

- 模式是内模式的逻辑表示；内模式是模式的物理实现；外模式是模式的逻辑子集

---

### 1.7 数据库系统的体系结构

- **单用户结构**：一台计算机独占，数据不共享
- **主从式结构**：一个主机带多个终端
- **客户/服务器结构（C/S）**：客户端负责界面，服务器负责DBMS功能
- **浏览器/服务器结构（B/S）**：三层C/S结构（浏览器-Web服务器-数据库服务器）
- **分布式结构（DDBS）**：数据分布在不同计算机上，支持全局应用，具有分布性、逻辑整体性、自治性、协作性
- **并行结构**：并行机上运行的数据库系统

---

### 1.8 数据库系统的组成

- **硬件平台**
- **软件系统**：DBMS、OS、语言工具与开发环境、应用软件
- **数据库（DB）**
- **各类人员**：DBA、系统分析员、应用程序员、用户

#### DBA的五大职责

1. 决定数据库中的信息内容和结构
2. 决定数据库的存储结构和存储策略
3. 定义数据的安全性要求和完整性约束条件
4. 监控数据库的使用和运行
5. 数据库的重组和重构

---

### 1.9 DBMS的功能

1. **数据定义功能**：提供DDL定义数据库中的数据对象
2. **数据组织、存储和管理**：分类组织存储各种数据，确定文件结构和存取方式
3. **数据操纵功能**：提供DML实现查询、插入、删除和修改
4. **事务管理和运行管理**：保证安全性、完整性、并发控制、故障恢复
5. **数据库的建立和维护功能**：数据装载、转储、恢复、重组织、性能监控
6. **其他功能**：通信、数据转换、异构互访

#### DBMS的工作过程

1. 应用程序向DBMS发出读记录命令
2. DBMS分析命令，调用子模式，检查存取权限
3. 调用模式，确定模式记录类型；通过模式/内模式映像找到内模式名
4. 调用内模式，确定物理记录
5. DBMS向OS发出读物理记录命令
6. OS执行读命令，数据读到系统缓冲区
7. DBMS按模式/子模式导出用户需要的记录形式
8. DBMS向应用程序送回状态信息
9. 记载日志
10. 应用程序检查状态信息，正常处理数据

## 第二章 关系模型

### 2.1 关系数据库的基本概念

#### 域（Domain）

- 一组具有相同数据类型的值的集合
- 域中所含值的个数称为域的**基数**

#### 笛卡尔积（Cartesian Product）

- $D_1 \times D_2 \times ... \times D_n = \{(d_1, d_2, ..., d_n) | d_i \in D_i\}$
- 其中每个元素$(d_1, d_2, ..., d_n)$称为一个**n元组**（n-Tuple）

#### 关系（Relation）

- $D_1 \times D_2 \times ... \times D_n$的**有意义的子集**称为关系
- 表示为 $R(D_1, D_2, ..., D_n)$
- n为关系的**度**（目）
- 关系可看作二维表：每行对应一个元组，每列称为属性

#### 关系中常用术语

| 术语                     | 定义                     |
| ---------------------- | ---------------------- |
| **候选码（Candidate Key）** | 能唯一标识一个元组的属性组，且不含多余属性  |
| **主码（Primary Key）**    | 从多个候选码中选定的一个           |
| **外码（Foreign Key）**    | 关系R的属性组X不是R的码，但是其他关系的码 |
| **全码（All Key）**        | 整个属性集合是候选码             |

#### 关系的六条性质

1. 每列的值都是同一类型
2. 每列具有不同的属性名（可同域）
3. 任意两元组不能完全相同
4. 行的次序可以互换
5. 列的次序可以互换
6. 分量值是**原子**的（不可再分）

#### 关系的三种类型

- **基本关系（基表）**：实际存在的表
- **查询表**：查询结果对应的表
- **视图表**：由基表或视图导出的虚表

---

### 2.2 关系模式与关系数据库

**关系模式**的形式化表示：$R(U, D, DOM, F)$

- R：关系名
- U：组成关系的属性名集合
- D：属性组U中属性所来自的域
- DOM：属性向域的映像集合
- F：属性间数据的依赖关系集合

简记：$R(U) = R(A_1, A_2, A_3, ..., A_n)$

**关系数据库**：所有实体及实体间联系的关系的集合构成。分**型**（关系模式集合）和**值**（某一时刻对应关系的集合）。

---

### 2.3 关系的三类完整性

#### （1）实体完整性

> 若属性A是基本关系R的**主码属性**，则属性A**不能取空值**。

- 实体具有唯一性标识——主码
- 主码中的属性（主属性）不能取空值

#### （2）参照完整性

> 若属性组F是R的**外码**，它与S的主码K相对应，则对于R中每个元组在F上的值必须为：
> 
> - 或者取**空值**（F的每个属性值均为空值）
> - 或者等于S中某个元组的**主码值**

- R为**参照关系**（依赖表），S为**被参照关系**（目标表）
- 外码和主码必须定义在同一个（或一组）域上

#### （3）用户定义的完整性

- 针对某一具体数据的约束条件，由应用环境决定
- 例：学生年龄在15~45之间，成绩在0~100之间

---

### 2.4 关系代数

关系代数是一种抽象的查询语言，用对关系的运算来表达查询。

#### 关系代数运算符

| 类别       | 运算符         | 含义     |
| -------- | ----------- | ------ |
| 集合运算符    | ∪           | 并      |
|          | −           | 差      |
|          | ∩           | 交      |
|          | ×           | 广义笛卡尔积 |
| 专门的关系运算符 | σ           | 选择     |
|          | π           | 投影     |
|          | ⋈           | 连接     |
|          | ÷           | 除      |
| 比较运算符    | ＞、≥、＜、≤、＝、≠ | 各类比较   |
| 逻辑运算符    | ¬、∧、∨       | 非、与、或  |

#### 五个基本运算

**并、差、笛卡尔积、投影、选择**（其他运算可用它们表示）

#### （1）集合并、交、差

要求：R和S具有**相同的目n**，相应属性取自**同一个域**

- **并**：$R \cup S = \{t | t \in R \lor t \in S\}$
- **差**：$R - S = \{t | t \in R \land t \notin S\}$
- **交**：$R \cap S = \{t | t \in R \land t \in S\} = R - (R - S)$

#### （2）广义笛卡尔积

R为n目关系（k₁个元组），S为m目关系（k₂个元组），则：
$R \times S$ 为 (n+m) 列、k₁×k₂ 个元组的集合

#### （3）选择运算 σ

$\sigma_F(R) = \{t | t \in R \land F(t) = true\}$

- 从**行**的角度进行的运算
- 产生同类关系

#### （4）投影运算 π

$\Pi_A(R) = \{t[A] | t \in R\}$

- 从**列**的角度进行的运算
- 消除重复元组
- 产生不同类关系

#### （5）连接运算 ⋈

**① 一般连接**：$R \underset{A\theta B}{\Join} S = \{t_r t_s | t_r \in R \land t_s \in S \land t_r[A] \theta t_s[B]\}$

**② 等值连接**：θ为"="的连接

**③ 自然连接**：R和S有同名属性Bᵢ，$R \Join S = \{t_r t_s | t_r \in R \land t_s \in S \land t_r[B] = t_s[B]\}$

- 形成的新关系中去掉**重复属性**
- **等值连接 vs 自然连接**：自然连接一定是等值连接（要求相等分量为公共属性，且去掉重复列）；等值连接不一定是自然连接

**④ 外连接**：保留原该舍弃的元组，在新增属性上填**空值（NULL）**

- 左外连接：保留左关系所有元组
- 右外连接：保留右关系所有元组
- 全外连接：保留两关系所有元组

#### （6）除运算 ÷

$R \div S = \{t_r[X] | t_r \in R \land \Pi_Y(S) \subseteq Y_x\}$

- 前提：R(X, Y)和S(Y, Z)有公共属性列
- 结果：P(X)，元组来自于R关系中，其象集包含$\Pi_Y(S)$

#### 关系代数表达式查询策略

- 一般形式：$\Pi...(\sigma...(R \times S))$ 或 $\Pi...(\sigma...(R \Join S))$
- 当查询涉及**否定或全部值**时，需要用**差操作或除操作**

---

### 2.5 查询优化

#### 查询优化的一般策略

1. **选择运算应尽可能先做**
2. 执行连接前对关系适当做**预处理**（建立索引、排序合并）
3. 把**投影运算和选择运算同时进行**
4. **投影运算**与其前后的双目运算同时进行
5. 合并**笛卡尔积与其后的选择**为连接运算
6. 找出**公共子表达式**，预先计算保存

#### 查询优化的步骤

1. 将查询表示成关系代数语法树
2. 根据变换规则转换成标准优化形式
3. 选择低层的操作算法
4. 生成、选择查询计划

## 第三章 关系数据库标准语言SQL

### 3.1 SQL概述

#### SQL的特点

1. **综合统一**：集DDL、DML、DCL于一体
2. **高度非过程化**：只需提出"做什么"，无需指明"怎么做"
3. **灵活的使用方式**：交互式、嵌入式
4. **面向集合的操作方式**
5. **简洁、通用、功能强**：核心功能仅用9个动词

#### SQL的核心动词

| SQL功能 | 动词                     |
| ----- | ---------------------- |
| 数据定义  | CREATE, DROP, ALTER    |
| 数据查询  | SELECT                 |
| 数据操纵  | INSERT, UPDATE, DELETE |
| 数据控制  | GRANT, REVOKE          |

#### SQL的三级层次结构

- **外模式** ↔ 视图（VIEW）
- **模式** ↔ 基本表（TABLE）
- **内模式** ↔ 存储文件 + 索引

---

### 3.2 数据定义

#### 模式定义

```sql
CREATE SCHEMA <模式名> AUTHORIZATION <用户名>;
DROP SCHEMA <模式名> {CASCADE | RESTRICT};
```

#### 表的创建与删除

```sql
-- 创建表
CREATE TABLE <表名> (
    <列名> <数据类型> [列约束条件],
    ...
    [表约束条件]
);

-- 删除表
DROP TABLE <表名> [CASCADE | RESTRICT];

-- 修改表
ALTER TABLE <表名>
    [ADD <新列名> <数据类型> [完整性约束]]
    [DROP <列名> [CASCADE|RESTRICT]]
    [MODIFY <列名> <数据类型>];
```

#### 常见数据类型

| 类型            | 含义             |
| ------------- | -------------- |
| CHAR(n)       | 定长字符串          |
| VARCHAR(n)    | 变长字符串          |
| INT / INTEGER | 长整数            |
| SMALLINT      | 短整数            |
| NUMERIC(p, d) | 定点数            |
| FLOAT(n)      | 浮点数            |
| DATE          | 日期（YYYY-MM-DD） |
| TIME          | 时间（HH:MM:SS）   |

#### 索引的建立

```sql
CREATE [UNIQUE] [CLUSTER] INDEX <索引名>
ON <表名> (<列名> [ASC|DESC], ...);

DROP INDEX <索引名>;
```

- **UNIQUE**：每个索引值只对应唯一数据记录
- **CLUSTER**：聚簇索引（索引项顺序与物理记录顺序一致），一个基本表最多建一个

### 3.3 数据查询（核心重点）

#### 基本格式

```sql
SELECT [ALL|DISTINCT] <目标列表达式> [别名], ...
FROM <表名或视图名> [别名], ...
[WHERE <条件表达式>]
[GROUP BY <列名1>, ... [HAVING <条件表达式>]]
[ORDER BY <列名2> [ASC|DESC], ...];
```

#### 单表查询

**（1）选择表中的列**

```sql
SELECT sname, sno, dept FROM Student;
SELECT sname, 2026-age AS Birth FROM Student;  -- 使用表达式和别名
```

**（2）选择表中的行**

- 比较：`WHERE grade < 60`
- 范围：`WHERE grade BETWEEN 85 AND 95`
- 确定集合：`WHERE dept IN ('信息院', '数学系')`
- 字符匹配：`WHERE sname LIKE '刘%'`（%表示任意长度，_表示单个字符）
- 转义：`LIKE '数据\_%原_' ESCAPE '\'`
- 空值：`WHERE grade IS NULL`（不能用=）

**（3）排序**

```sql
ORDER BY dept, age DESC;  -- 先按系升序，同系按年龄降序
```

**（4）聚集函数**

| 函数                       | 作用        |
| ------------------------ | --------- |
| `COUNT(*)`               | 统计元组个数    |
| `COUNT([DISTINCT] <列名>)` | 统计一列中值的个数 |
| `SUM(<列名>)`              | 计算数值列总和   |
| `AVG(<列名>)`              | 计算数值列平均值  |
| `MAX(<列名>)`              | 求最大值      |
| `MIN(<列名>)`              | 求最小值      |

**（5）分组（GROUP BY）**

```sql
-- 求每个学生的平均成绩
SELECT sno, AVG(grade) FROM SC GROUP BY sno;

-- 筛选平均成绩>88的学生
SELECT sno, AVG(grade) FROM SC GROUP BY sno HAVING AVG(grade) > 88;
```

> **WHERE vs HAVING**：WHERE在分组前筛选行；HAVING在分组后筛选组

---

#### 连接查询

**等值连接**

```sql
SELECT Student.*, SC.* FROM Student, SC WHERE Student.Sno = SC.Sno;
```

**自然连接**

```sql
SELECT * FROM Student NATURAL JOIN SC;
```

**自身连接**

```sql
SELECT s1.sname, s1.age FROM Student s1, Student s2
WHERE s1.age > s2.age AND s2.sname = '王迎';
```

**外连接**

```sql
-- 左外连接：保留Student中所有元组（包括未选课学生）
SELECT * FROM Student LEFT OUTER JOIN SC;

-- 右外连接、全外连接：RIGHT OUTER JOIN, FULL OUTER JOIN
```

**复合条件连接**

```sql
SELECT Student.Sno, Sname FROM Student, SC
WHERE Student.Sno = SC.Sno AND SC.Cno = '2' AND SC.Grade > 90;
```

---

#### 嵌套查询

**带有IN谓词的子查询（不相关子查询）**

```sql
SELECT sno, sname, dept FROM Student
WHERE dept IN (SELECT dept FROM Student WHERE sname = '刘晨');
```

**带有比较运算符的子查询**

```sql
SELECT sname FROM Student
WHERE age > (SELECT AVG(age) FROM Student);
```

**带有ANY(SOME)或ALL谓词的子查询**

```sql
-- 查询其他系比信息院所有学生年龄都小的学生
-- 查询平均成绩最高的学生号
SELECT sno FROM SC GROUP BY sno
HAVING AVG(grade) >= ALL (SELECT AVG(grade) FROM SC GROUP BY sno);
```

**带有EXISTS谓词的子查询（相关子查询）**

- EXISTS：内层查询结果**非空**时返回真

- NOT EXISTS：内层查询结果**为空**时返回真
  
  ```sql
  -- 查询选修了全部课程的学生姓名（双重否定）
  SELECT sname FROM Student WHERE NOT EXISTS
  (SELECT * FROM Course WHERE NOT EXISTS
    (SELECT * FROM SC WHERE SC.sno = Student.sno AND SC.cno = Course.cno));
  ```

> **不相关子查询 vs 相关子查询**：
> 
> - 不相关：子查询条件不依赖父查询，由里向外处理
> - 相关：子查询条件依赖父查询，外层每取一个元组就执行一次内层

---

#### 集合查询

```sql
-- 并 UNION（去重）/ UNION ALL（保留重复）
SELECT * FROM Student WHERE Sdept = 'CS'
UNION
SELECT * FROM Student WHERE Sage <= 19;

-- 交 INTERSECT
-- 差 EXCEPT
```

### 3.5 视图

#### 视图的概念

- 从一个或几个基本表（或视图）导出的**虚表**
- 数据库中只存放视图的**定义**，不存放对应数据
- 对视图的一切操作最终转换为对**基本表**的操作

#### 视图的作用

1. 简化结构及复杂操作
2. 多角度、灵活地共享数据
3. 提供安全保护
4. 提高逻辑独立性

#### 创建视图

```sql
CREATE VIEW <视图名> [(<列名>, ...)]
AS <子查询>
[WITH CHECK OPTION];  -- 更新时保证满足视图定义的谓词条件
```

#### 视图更新限制

以下情况视图**不允许更新**：

- 由两个或以上基本表导出的
- 列来自表达式或常数（不可INSERT和UPDATE）
- 列来自聚集函数
- 定义含有GROUP BY子句
- 定义含有DISTINCT短语
- 含有嵌套查询且内层FROM涉及导出视图的基本表

### 3.6 嵌入式SQL

#### 嵌入式SQL需解决的三个问题

1. **区分SQL与主语言语句**：前缀加`EXEC SQL`，结束用分号
2. **区分主变量与列变量**：主变量前加**冒号**（如 `:Cname`）
3. **集合处理与单记录处理的协调**：使用**游标（Cursor）**机制

#### 游标使用步骤

1. **定义游标**：`EXEC SQL DECLARE <游标名> CURSOR FOR <SELECT语句>;`
2. **打开游标**：`EXEC SQL OPEN <游标名>;`
3. **推进游标**：`EXEC SQL FETCH <游标名> INTO :<主变量>, ...;`
4. **关闭游标**：`EXEC SQL CLOSE <游标名>;`

#### 通信方式

- 主语言 → SQL语句：通过**输入主变量**提供参数
- SQL语句 → 主语言：通过**输出主变量**和**SQLSTATE状态变量**传递执行状态

```
用户标识和鉴别 → DBMS存取控制 → OS安全保护 → 数据密码存储
```

### 4.3 存取控制

#### （1）自主存取控制（DAC）

- 基于授予和收回权限的机制
- 通过SQL的**GRANT**和**REVOKE**语句实现
- 灵活但防护等级较低，可能"无意泄露"

#### （2）强制存取控制（MAC）

- 每个数据对象有**密级**（Label），每个用户有**许可证级别**
- 读取规则：主体许可证级别 ≥ 客体密级
- 写入规则：主体许可证级别 ≤ 客体密级
- 适用于军事、政府等有严格固定密级分类的场合



### 5.5 触发器（Trigger）

#### 概念

- 用户定义在关系表上的一类由**事件驱动**的特殊**存储过程**
- 一旦定义，任何用户对表的增删改操作均由服务器**自动激活**

#### 触发器的组成

1. **触发事件**：INSERT、DELETE、UPDATE
2. **触发条件**：WHEN子句指定
3. **触发动作**：SQL语句/存储过程

#### 创建触发器

```sql
CREATE TRIGGER <触发器名>
{BEFORE | AFTER | INSTEAD OF} <触发事件>
ON <表名>|<视图名>
[REFERENCING [OLD AS <旧元组变量>] [NEW AS <新元组变量>]]
[FOR EACH {ROW | STATEMENT}]
[WHEN <触发条件>]
<触发动作体>;
```

#### 触发器类型

- **BEFORE触发器**（前触发器）：在触发事件之前执行，可接受或终止操作
- **AFTER触发器**（后触发器）：在触发事件改变数据库之后执行
- **INSTEAD OF触发器**（替换触发器）：替换视图上的更新操作
- **行级触发器**（FOR EACH ROW）：每变更一行触发一次
- **语句级触发器**（FOR EACH STATEMENT）：每次SQL语句触发一次

#### 触发器的执行顺序

1. 执行该表上的BEFORE触发器
2. 激活触发器的SQL语句
3. 执行该表上的AFTER触发器

#### 触发器 vs 存储过程

- 存储过程：由用户**显式调用**执行
- 触发器：当触发事件发生、触发条件成立时由DBMS**隐式调用**执行

## 第六章 关系数据理论

### 6.1 问题的提出

#### 关系模式设计不合理带来的问题

1. **数据冗余度高**：相同数据重复存储多次
2. **数据修改复杂**：容易造成数据不一致
3. **插入异常**：应该插入的数据不能执行插入操作
4. **删除异常**：不应该删除的数据被删除

**原因**：关系存在多余的数据依赖或不够规范
**解决**：关系模式分解（关系规范化）

---

### 6.2 函数依赖

#### 基本概念

**函数依赖**：设R(U)是属性U上的关系模式，X、Y是U的子集。若对R的任意关系r中任意两个元组s、t，由 $s[X] = t[X]$ 能导致 $s[Y] = t[Y]$，则称**X函数决定Y**或**Y函数依赖于X**，记作 $X \rightarrow Y$。

**几种函数依赖关系**：

- **非平凡函数依赖**：$X \rightarrow Y$，但 $Y \nsubseteq X$
- **平凡函数依赖**：$X \rightarrow Y$，但 $Y \subseteq X$
- **完全函数依赖**：$X \xrightarrow{F} Y$，且对X的任何真子集X'，都有 $X' \nrightarrow Y$
- **部分函数依赖**：$X \xrightarrow{P} Y$，且存在X的真子集X'使得 $X' \rightarrow Y$
- **传递函数依赖**：$X \rightarrow Y$，$Y \nrightarrow X$，$Y \rightarrow Z$，则 $X \xrightarrow{T} Z$

> 左部为**单属性**的函数依赖一定是**完全函数依赖**。

#### 候选键

设X为R<U, F>中的属性或属性组合，若 $X \xrightarrow{F} U$，则X为R的**候选键**。

相关术语：

- **主属性**：候选键中的属性
- **非主属性**：不在任何候选键中的属性
- **全码**：整个属性组为关键字

---

### 6.3 关系范式

#### 规范化

把一个**低一级范式**的关系模式通过**模式分解**转化为若干个**高一级范式**的关系模式的过程。

#### 范式等级关系

```
1NF ⊃ 2NF ⊃ 3NF ⊃ BCNF ⊃ 4NF
```

---

#### 第一范式（1NF）

> 若R的每个属性值都是**不可再分的最小数据单元**，则 R∈1NF。

- 1NF是关系模式的**最低要求**
- 从型上看：不存在嵌套结构
- 从值上看：不存在重复组、表达式

---

#### 第二范式（2NF）

> 若 R∈1NF，且R中的每一个**非主属性**都**完全函数依赖**于R的任一候选键，则 R∈2NF。

**分解为2NF的方法**：将非主属性和候选键之间满足部分函数依赖和完全函数依赖的属性分解到不同的关系中。

> **结论**：若关系的候选键是**单属性**的，则该关系至少是2NF。

---

#### 第三范式（3NF）

> 若 R∈1NF，且R的任何一个**非主属性**都**不传递函数依赖**于它的任何一个候选键，则 R∈3NF。

**分解为3NF的方法**：将涉及传递函数依赖的属性分解到不同的关系中。

> **结论**：
> 
> - 一个3NF关系必定是2NF
> - 若关系的**所有属性都是主属性**，则该关系至少是3NF

**达到3NF仍可能存在的问题**（以SCT关系为例）：

- 插入异常：新课程和教师无法插入（没有学生选课）
- 删除异常：删除选课记录会丢失课程与教师数据

---

#### BC范式（BCNF）

> 关系模式R<U, F>∈1NF。若F中所有函数依赖 $X \rightarrow Y (Y \nsubseteq X)$ 的左部X都**包含R的任一候选键**，则 R∈BCNF。

- 一个BCNF关系必定是3NF
- **消除主属性对码的部分和传递函数依赖**

> **结论**：**任何二元关系必定是BCNF**。

---

#### 各范式的问题与解决方法

| 范式       | 要消除的问题            | 分解方法              |
| -------- | ----------------- | ----------------- |
| 1NF→2NF  | 非主属性对候选键的部分函数依赖   | 将满足部分和完全函数依赖的属性分开 |
| 2NF→3NF  | 非主属性对候选键的传递函数依赖   | 将传递依赖涉及的属性分开      |
| 3NF→BCNF | 主属性对候选键的部分和传递函数依赖 | 消除决定因素非码的非平凡函数依赖  |

---

### 6.4 Armstrong公理系统

对关系模式R<U, F>，U为全体属性集，F为U上的函数依赖集：

- **A1 自反律**：若 $Y \subseteq X \subseteq U$，则 $X \rightarrow Y$
- **A2 增广律**：若 $X \rightarrow Y$，则 $XZ \rightarrow YZ$
- **A3 传递律**：若 $X \rightarrow Y$、$Y \rightarrow Z$，则 $X \rightarrow Z$

#### 推论

- **合并规则**：若 $X \rightarrow Y$、$X \rightarrow Z$，则 $X \rightarrow YZ$
- **分解规则**：若 $X \rightarrow YZ$，则 $X \rightarrow Y$、$X \rightarrow Z$
- **伪传递规则**：若 $X \rightarrow Y$、$WY \rightarrow Z$，则 $WX \rightarrow Z$

---

### 6.5 属性闭包 $X_F^+$

**定义**：$X_F^+ = \{A | X \rightarrow A \text{ 能由F用Armstrong公理导出}\}$

**定理**：$X \rightarrow Y$ 能从F中用Armstrong公理导出的充要条件是 $Y \subseteq X_F^+$

**求闭包算法**：

1. $X^{(0)} = X$
2. $X^{(i+1)} = X^{(i)} \cup A$（其中对F中任一个 $Y \rightarrow A$，且 $Y \subseteq X^{(i)}$）
3. 若 $X^{(i+1)} = X^{(i)}$ 或 $X^{(i+1)} = U$ 则结束

> 若 $X_F^+ = U$，则X为R的**候选键**。

---

### 6.6 求候选键的方法

将属性分为四类：

| 类别       | 定义         | 与候选键的关系    |
| -------- | ---------- | ---------- |
| **L类**   | 仅出现在F左部的属性 | 必为任一候选键的成员 |
| **R类**   | 仅出现在F右部的属性 | 不是任一候选键的成员 |
| **LR类**  | 左右都出现的属性   | 可能是候选键成员   |
| **NLR类** | 左右都未出现的属性  | 必为任一候选键的成员 |

> 若X是**L类和NLR类**属性组成的属性集，且 $X_F^+ = U$，则X为R的**唯一候选键**。

---

### 6.7 最小函数依赖集 $F_m$

**定义**：满足以下三个条件的函数依赖集：

1. F中每个函数依赖的**右部都是单属性**
2. F中不存在**多余的函数依赖**（去掉任何一条都不等价）
3. F中每个函数依赖的**左部没有多余的属性**

**求解步骤**：

1. **分解**：使右部仅含单属性
2. **去左部多余属性**：对 $XY \rightarrow A$，在F中求 $X^+$，若 $A \subseteq X^+$，则Y多余
3. **去多余函数依赖**：对 $X \rightarrow A$，在 $F - \{X \rightarrow A\}$ 中求 $X^+$，若 $A \subseteq X^+$，则该依赖多余

---

### 6.8 关系模式分解

#### 分解的两个标准

1. **无损连接性**：$r = \Pi_{R1}(r) \Join \Pi_{R2}(r) \Join ... \Join \Pi_{Rk}(r)$
2. **保持函数依赖性**：$F \equiv \Pi_{R1}(F) \cup \Pi_{R2}(F) \cup ... \cup \Pi_{Rk}(F)$

#### 二项分解定理

分解 $\rho = (R_1, R_2)$ 具有无损连接性的充要条件：
$$R_1 \cap R_2 \rightarrow (R_1 - R_2) \in F^+ \quad \text{或} \quad R_1 \cap R_2 \rightarrow (R_2 - R_1) \in F^+$$

## 第七章 数据库设计

### 7.1 数据库设计概述

**数据库设计**：对于一个给定的应用环境，构造（设计）最优的数据模型，建立数据库及其应用系统，使之能有效存储数据，满足各种用户需求。

#### 数据库设计的六大步骤

```
需求分析 → 概念结构设计 → 逻辑结构设计 → 物理设计 → 实施 → 运行维护
```

---

### 7.2 需求分析

#### 任务

- 收集用户需求，明确新系统功能
- 重点：**信息要求**、**处理要求**、**安全性与完整性要求**

#### 工具

- **数据流图（DFD）**：描述业务流程中数据和处理的关系
  - 基本成分：数据存储、数据处理、数据流、外部实体
- **数据字典（DD）**：系统中各类数据描述的集合
  - 内容：数据项、数据结构、数据流、数据存储、处理过程

---

### 7.3 概念结构设计

#### 任务

将需求分析得到的用户需求抽象为**信息结构（概念模型）**。

#### 设计方法

- **自顶向下**：先定义全局框架，逐步细化
- **自底向上**：先设计各局部E-R图，再集成为全局E-R图（**最常用**）
- **逐步扩张**：先定义核心概念，向外扩充
- **混合策略**：自顶向下与自底向上结合

#### 自底向上方法的步骤

1. **数据抽象与局部视图设计**：设计各个分E-R图
2. **视图集成（全局视图设计）**：合并分E-R图，消除冲突和冗余

#### 分E-R图合并时的三类冲突

| 冲突类型     | 含义                    | 解决方法     |
| -------- | --------------------- | -------- |
| **属性冲突** | 属性值类型、取值范围不同          | 尽量大的覆盖   |
| **命名冲突** | 同名异义或异名同义             | 重新命名     |
| **结构冲突** | 同一对象在不同视图中抽象不同、属性组成不同 | 统一抽象、取并集 |

#### E-R图扩展概念

- **聚集 vs 概括（继承）**
- **弱实体**：依赖其他实体存在的实体
- **多值属性**：可分解或提升为弱实体集
- **复合属性**：可提升为实体集

---

### 7.4 逻辑结构设计

#### 任务

将基本E-R模型转换为DBMS所支持的数据模型（关系模型）。

#### E-R模型向关系模型转换规则

| 对象       | 转换规则                  |
| -------- | --------------------- |
| 实体型      | 转换为一个关系模式             |
| 1:1联系    | 可转换为独立关系模式，或与任一端合并    |
| 1:n联系    | 可转换为独立关系模式，或与n端合并（外键） |
| m:n联系    | **必须**转换为一个独立的关系模式    |
| 多元联系     | 转换为一个独立关系模式           |
| 相同键的关系模式 | 可合并                   |

#### 数据模型的优化

1. 分析数据依赖
2. 对数据依赖进行极小化处理
3. 确定各关系模式所属范式
4. 根据处理需求对模式进行合并或分解
5. 必要时进行**水平分解**或**垂直分解**

#### 反规范化设计

- 增加派生列
- 增加冗余列
- 物化视图

---

### 7.5 数据库物理设计

#### 目标

设计优化的物理数据库结构，使响应时间短、空间利用率高、事务吞吐率大。

#### 主要内容

1. **存取方法设计**：索引的选择和设计
2. **存储结构设计**：数据存放位置、系统配置参数

#### 索引建立原则

**不适合建立索引的情况**：

- 太小的表
- 不出现或很少出现在查询条件中的属性
- 经常更新的属性和表
- 属性值取值个数很少（如性别）
- 属性值分布严重不均

**适合建立索引的情况**：

- 主键和外键上
- 经常按某列顺序访问
- 常用于 WHERE、ORDER BY、GROUP BY、DISTINCT 的列
- 经常用于连接操作的列
- 经常作为聚集函数的列

#### 聚簇索引建立原则

- 通过聚簇码进行访问是**主要应用**
- 每个聚簇码值的平均元组数**适中**
- 聚簇码值**相对稳定**

## 第八章 数据库恢复技术

### 8.1 事务的基本概念

#### 事务（Transaction）

- 用户定义的一个数据库操作序列，**要么全做，要么全不做**，是不可分割的工作单位
- 事务是**恢复和并发控制**的基本单位

#### SQL事务定义

```sql
BEGIN TRANSACTION;
    SQL语句1;
    SQL语句2;
    ...
COMMIT;      -- 事务提交
-- 或
ROLLBACK;    -- 事务回滚
```

#### 事务的三种运行模式

1. **自动提交事务**：每条单独语句都是一个事务
2. **显式事务**：以BEGIN TRANSACTION显式开始，COMMIT/ROLLBACK显式结束
3. **隐性事务**：上事务完成时新事务隐式启动

---

### 8.2 事务的ACID特性

| 特性                   | 含义                           |
| -------------------- | ---------------------------- |
| **原子性（Atomicity）**   | 事务中所有操作要么全做，要么全不做            |
| **一致性（Consistency）** | 事务执行结果使数据库从一个一致性状态变为另一个一致性状态 |
| **隔离性（Isolation）**   | 并发执行的事务互不干扰                  |
| **持久性（Durability）**  | 事务一旦提交，对数据库的改变是永久性的          |

#### 破坏ACID的因素

1. 多个事务并行运行时，不同事务的操作交叉执行
2. 事务在运行过程中被强行停止

---

### 8.3 故障的种类与恢复策略

| 故障类型          | 特征                  | 恢复策略                  |
| ------------- | ------------------- | --------------------- |
| **事务故障**      | 事务未运行至正常终止点         | UNDO（撤销）未完成事务         |
| **系统故障（软故障）** | 系统停机，影响所有运行事务，不破坏DB | UNDO未完成事务 + REDO已提交事务 |
| **介质故障（硬故障）** | 外存损坏，破坏数据库          | 装入后备副本 + REDO已完成事务    |

---

### 8.4 恢复的实现技术

#### 数据转储（Backup）

- **静态转储**：无运行事务时转储，得一致性副本（但降低可用性）
- **动态转储**：转储期间允许存取，需配合日志文件
- **海量转储**：每次全库转储
- **增量转储**：每次只转储上次转储后更新过的数据

#### 日志文件（Logging）

- 记录事务对数据库的更新操作
- 格式：事务标识、操作类型、操作对象、**更新前值**、**更新后值**

#### 登记日志文件的两条原则

1. 登记的次序严格按**并发事务执行的时间次序**
2. **必须先写日志文件，后写数据库**（日志超前写规则）

---

### 8.5 检查点恢复技术

#### 目的

- 避免搜索整个日志文件的巨大时间开销
- 避免对已写入数据库的事务重复执行REDO

#### 检查点记录内容

- 建立检查点时刻所有**正在执行的事务清单**
- 各事务**最近一个日志记录的地址**

#### 利用检查点的恢复步骤

1. 找到最后一个检查点记录
2. 得到检查点时刻正在执行的事务清单（放入UNDO队列）
3. 从检查点正向扫描日志：
   - 新开始的事务 → 放入UNDO队列
   - 提交的事务 → 从UNDO移到REDO队列
4. 对UNDO队列执行UNDO，对REDO队列执行REDO

---

### 8.6 数据库镜像

- 自动把整个数据库或关键数据复制到另一个磁盘
- **作用**：介质故障时由镜像磁盘继续提供服务，无需关闭系统
- 实际应用中往往只对**关键数据和日志文件**进行镜像

#### 远程备份

- 主站点执行事务处理，备份站点应付突发事件
- 同步方法：传送日志记录到备份站点执行同样操作（**不是传送数据本身**）

---

## 第九章 并发控制

### 9.1 并发控制概述

#### 事务的三种执行方式

1. **串行执行**：每一时刻只有一个事务运行（效率低）
2. **交叉并发方式**：单处理机中事务操作轮流交叉运行
3. **同时并发方式**：多处理机中多个事务真正并行运行

#### 并发操作带来的三类数据不一致性

| 问题                             | 含义                  | 解决方法   |
| ------------------------------ | ------------------- | ------ |
| **丢失修改（Lost Update）**          | T1的修改被T2覆盖          | 一级封锁协议 |
| **不可重复读（Non-repeatable Read）** | T1两次读同一数据结果不同       | 三级封锁协议 |
| **读"脏"数据（Dirty Read）**         | T2读到T1未提交的修改，T1后来回滚 | 二级封锁协议 |

---

### 9.2 封锁（Locking）

#### 两种基本锁类型

| 锁类型            | 含义        | 其他事务       |
| -------------- | --------- | ---------- |
| **排它锁（X锁/写锁）** | 事务T可读可修改A | 不能对A加任何锁   |
| **共享锁（S锁/读锁）** | 事务T可读不可改A | 可加S锁，不可加X锁 |

---

### 9.3 三级封锁协议

| 协议级别   | 加锁规则              | 防止的问题             |
| ------ | ----------------- | ----------------- |
| **一级** | 修改前加X锁，事务结束释放     | 丢失修改              |
| **二级** | 一级 + 读前加S锁，读完释放S锁 | 丢失修改 + 脏读         |
| **三级** | 一级 + 读前加S锁，事务结束释放 | 丢失修改 + 脏读 + 不可重复读 |

> 三级封锁协议不能保证得到**可串行化调度**，也会造成死锁。

---

### 9.4 活锁和死锁

#### 活锁

- 某事务永远处于等待状态而得不到执行
- **避免方法**：**先来先服务**

#### 死锁

- 并发事务在没有任何外力作用下都无法执行下去的僵持状态

##### 预防死锁

1. **一次封锁法**：一次将所需数据全部加锁（降低并发度，难以预知封锁对象）
2. **顺序封锁法**：按预定顺序封锁（难以维护顺序）

##### 诊断死锁

1. **超时法**：等待超时则认为死锁（时限难把握）
2. **等待图法**：用有向图表示等待关系，检测**回路**

##### 解除死锁

选择处理代价最小的**事务撤销**，释放其持有的所有锁。

---

### 9.5 并发调度的可串行性

#### 可串行化调度

- 事务的并发执行结果与**某个串行执行结果相同**的调度
- 可串行化调度是**正确调度**的判别准则

#### 冲突可串行化

- 不同事务的**冲突操作**（读-写、写-写）次序不变，能通过交换不冲突操作变为串行调度
- 冲突可串行化是**可串行化的充分条件**（不是必要条件）

---

### 9.6 两段锁协议（2PL）

#### 定义

所有事务必须分两个阶段对数据项加锁和解锁：

1. **扩展阶段（Growing Phase）**：可申请任何锁，**不能释放**任何锁
2. **收缩阶段（Shrinking Phase）**：可释放任何锁，**不能申请**新锁

> **事务遵守两段锁协议是可串行化调度的充分条件，而不是必要条件。**

#### 两段锁协议 vs 一次封锁法

- 一次封锁法遵守两段锁协议
- 两段锁协议不要求一次性加锁，因此遵守两段锁协议的事务仍可能发生死锁

---

### 9.7 封锁的粒度

#### 封锁粒度与系统开销

- 封锁粒度**越大** → 并发度**越小**，系统开销**越小**
- 封锁粒度**越小** → 并发度**越高**，系统开销**越大**

#### 封锁粒度选择原则

- 处理大量元组的事务 → 以**关系**为封锁粒度
- 处理少量元组的事务 → 以**元组**为封锁粒度
- 处理多个关系大量元组 → 以**数据库**为封锁粒度

#### 多粒度封锁与意向锁

**多粒度树**：数据库 → 关系 → 元组 → 列

三种意向锁：

- **IS锁（意向共享锁）**：后裔结点拟加S锁
- **IX锁（意向排它锁）**：后裔结点拟加X锁
- **SIX锁（共享意向排它锁）**：S + IX

**加锁原则**：

- 申请封锁时按**自上而下**的次序
- 释放封锁时按**自下而上**的次序
- 对任一结点加锁，必须先对上层结点加意向锁

## 附录：重要公式与速记要点

### 关系代数基本运算表示

- 交：$R \cap S = R - (R - S)$
- 连接：$R \underset{i\theta j}{\Join} S = \sigma_{[i]\theta[m+j]}(R \times S)$
- 自然连接：$R \Join S = \Pi_{i_1,i_2,...i_m}(\sigma_{R.A_1=S.A_1 \land ... \land R.A_k=S.A_k}(R \times S))$
- 除：$R \div S \equiv \Pi_X(R) - \Pi_X((\Pi_X(R) \times \Pi_Y(S)) - R)$

### 范式判定速查

| 条件          | 此关系至少是 |
| ----------- | ------ |
| 候选键都是单属性    | 2NF    |
| 所有属性都是主属性   | 3NF    |
| 二元关系        | BCNF   |
| 左部为单属性的函数依赖 | 完全函数依赖 |

```sql
-- 完整查询格式
SELECT [DISTINCT] 目标列

```

### 事务与恢复

```
事务故障 → UNDO（反向扫描日志，用更新前值）

```

### 封锁协议速查

```
一级封锁：X锁 + 事务结束释放 → 防止丢失修改
二级封锁：一级 + S锁 + 读完释放 → 增加防止脏读

```
